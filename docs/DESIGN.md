# Choix et périmètre

Étude avant création du dépôt : deux dépôts C++ récents, un backend Python, une application Flutter et aperçu de la liste des dépôts du propriétaire. Les deux projets C++ emploient CMake/C++17, `Source/`, `tests/`, README d’installation, Actions main/PR/tag `v*`, tests avant publication, ZIP Windows et SHA256SUMS. Cette structure est conservée ; aucun code privé n’est copié. Pas de bibliothèque JUCE : elle n’apporte rien à ce widget.

Alternatives examinées : [KAgenda](https://github.com/aamaral14/KAgenda), Plasma 6/QML avec intégration Google ; [Rainmeter-Todo-Skin](https://github.com/MHJoy99/Rainmeter-Todo-Skin), Rainmeter/Windows. Ni l’un ni l’autre ne fournit un cœur C++ léger partagé sur les deux systèmes. Win32 + Plasmoid demanderait deux interfaces et deux chemins OAuth. Qt Widgets conserve une seule interface, le réseau natif Qt et aucun moteur web. Le navigateur système n’est ouvert que pour OAuth. QtKeychain utilise le coffre du système, sans repli sur un fichier en clair.

Intégration : X11, fenêtre de type bureau via EWMH ; Plasma Wayland, couche basse layer-shell-qt avec focus à la demande ; Windows, fenêtre enfant du WorkerW d’Explorer (technique non documentée par Microsoft, option fenêtre normale disponible). Dimensions/position configurables ; pas d’éditeur de tâches, suppression, notifications, pièces jointes ou ordonnancement personnalisé.

Synchronisation : un seul cycle réseau à la fois, requêtes séquentielles et pagination complète. Rafraîchissement 120 s (30–3600 s), actions immédiates, timeout 20 s, recul exponentiel sur erreur jusqu’à 15 min et respect de Retry-After. Pas de polling à la seconde ni de backend. Lecture complète de toutes les listes pour conserver un cache cohérent, filtre local. Les changements Android sont visibles au prochain cycle. PATCH ne modifie que le statut : dernier changement local envoyé gagnant. Les éditions en attente sont superposées aux réponses du serveur.

Cache/outbox JSON versionné écrit atomiquement avant tout envoi. Une seule instance par profil. Si l’écriture échoue, aucune mutation réseau n’est envoyée. Aucun jeton dans le cache. Les titres sont privés mais le cache n’est pas chiffré : protection par permissions utilisateur et chiffrement du disque conseillé.

Google Tasks ne propose pas de clé d’idempotence pour POST. Un ajout dont la réponse est perdue est marqué incertain et n’est jamais réessayé automatiquement. L’utilisateur vérifie Google Tasks puis confirme explicitement la nouvelle tentative (risque de doublon). Un PATCH est idempotent et peut être réessayé. Pas de suppression locale des opérations en échec permanent : statut visible et reconnexion/nouvelle tentative explicite.

OAuth : client « Desktop app », navigateur externe, boucle locale IPv4 sur port aléatoire, state aléatoire et PKCE S256, scope Tasks uniquement. Import local du JSON du client. Le client_secret d’une application publique n’est pas un secret confidentiel mais reste hors dépôt par principe. Refresh token dans KWallet/Secret Service ou Windows Credential Manager via QtKeychain ; access token seulement en mémoire. Les réponses OAuth et les en-têtes Authorization ne sont jamais journalisés.

Projet Cloud dédié créé, Tasks API activée avec le compte propriétaire disponible. Son identifiant reste dans les notes locales, pas dans le dépôt. Aucun projet existant modifié. Le navigateur de la VM n’a pas de session Google. gcloud IAP ne crée que des clients IAP, pas des clients desktop ; ne pas l’utiliser comme contournement. Configuration du consentement et création du client desktop à faire dans Google Auth Platform. Les tests réseau automatisés utilisent un serveur local, pas un compte personnel. Un test réel OAuth/Tasks reste nécessaire avant de déclarer la release validée de bout en bout.
